## 4.1 引擎选型

| 维度      | Cocos Creator 3.8 LTS + TS | PixiJS 8 自研    |
| ------- | -------------------------- | -------------- |
| 抖音小游戏导出 | 官方构建目标，一键出包                | 需自己写适配、分包、生命周期 |
| 分包与首包控制 | 内置分包、资源依赖分析                | 全部手写           |
| UI 系统   | 内置节点树 + 九宫格 + 适配           | 需自建布局系统        |
| 图集/资源管理 | 内置 Asset Bundle            | 手写 loader      |
| H5 出口   | 一键构建                       | 天然支持           |
| 包体      | 需裁剪引擎模块（可压到 \~1.2MB）       | 可做到 <400KB     |
| 团队成本    | 低（单人可维护）                   | 高（UI/适配/分包全自建） |
| 与原型的关系  | 逻辑规则照搬，渲染重写                | 逻辑与渲染都可渐进迁移    |

**结论：选 Cocos Creator 3.8 LTS + TypeScript。**

理由不是"引擎更强"，而是**这个项目的复杂度集中在平台适配和资源管线，而不是渲染**。抖音小游戏的登录、广告、分享、订阅消息、侧边栏、生命周期、分包、审核合规，每一项都是坑；Cocos 把这些做成了官方构建目标，而 PixiJS 需要全部自研。用 PixiJS 省下的 800KB 包体，换不回自建 UI 与适配层的时间成本。

保留的退路：所有业务逻辑（数值、存档、探险结算、经济）写成**不依赖引擎的纯 TS 模块**，通过事件总线与渲染层通信。如果后续发现 Cocos 包体或性能不达标，渲染层可替换为 PixiJS，不改逻辑。

## 4.2 分层结构

```
src/
├── platform/        # 平台实现：douyin.ts / h5.ts / mock.ts
├── data/            # 存档读写、迁移、配置加载、schema 校验
├── core/            # 纯逻辑：状态机、数值结算、经济、探险、成就
├── view/            # 场景、角色、动画、特效
├── ui/              # 面板、HUD、弹窗、引导
└── config/          # JSON 配置（构建时打包，不远程）
```

依赖方向严格单向：`view/ui → core → data → platform`。`core` 不 import 任何 `cc` 模块，保证可单测、可迁移。

模块职责：

| 层        | 职责                                | 禁止       |
| -------- | --------------------------------- | -------- |
| platform | 登录、广告、分享、存储、系统信息、生命周期、订阅消息、侧边栏、埋点 | 不含任何游戏规则 |
| data     | 配置校验、存档序列化/反序列化、版本迁移、备份           | 不直接改 UI  |
| core     | 数值 tick、动作结算、探险派遣与结算、经济校验、成就判定    | 不持有节点引用  |
| view     | 房间渲染、角色动画状态机、拖拽摆放、粒子              | 不写存档     |
| ui       | 面板栈、引导、Toast、数值条                  | 不写业务规则   |

## 4.3 平台适配层接口清单

```ts
export interface IPlatform {
  readonly name: 'douyin' | 'h5' | 'mock';
  login(): Promise<{ openId: string; nickname?: string }>;
  getSystemInfo(): Promise<{ screenW: number; screenH: number; safeTop: number; safeBottom: number; pixelRatio: number; platform: string }>;
  storage: {
    get(key: string): Promise<string | null>;
    set(key: string, value: string): Promise<void>;
    remove(key: string): Promise<void>;
  };
  ad: {
    isRewardedReady(slot: string): boolean;
    showRewarded(slot: string): Promise<'completed' | 'skipped' | 'failed'>;
    showBanner(slot: string): void;
    hideBanner(): void;
  };
  share(opts: { title: string; imageUrl?: string; query?: string }): Promise<'success' | 'cancel' | 'fail'>;
  subscribeMessage(tmplIds: string[]): Promise<{ accepted: string[]; rejected: string[] }>;
  sidebar: {
    isSupported(): boolean;
    checkEnterFromSidebar(): Promise<boolean>;
    navigateToSidebar(): Promise<void>;
  };
  lifecycle: {
    onShow(cb: () => void): void;
    onHide(cb: () => void): void;
  };
  analytics: {
    track(event: string, params?: Record<string, string | number>): void;
  };
  vibrate(type: 'light' | 'medium'): void;
  getLaunchQuery(): Record<string, string>;
}
```

H5 端实现同一个接口：`ad.showRewarded` 走一个 3 秒模拟播放的弹窗（开发期），上线 H5 时替换为联盟广告 SDK；`storage` 用 localStorage；`sidebar` 返回 false。**这样保证"同一份代码，两个出口"，也保证本地调试不需要真机。**

存储策略（直接解决原型问题 6）：

| 槽位                 | 写入时机                               | 覆盖规则         |
| ------------------ | ---------------------------------- | ------------ |
| `save_auto`        | 每 30 秒 + onHide + 关键节点（探险派遣/领取/购买） | 只写自己，永不写手动槽  |
| `save_manual_1..3` | 用户主动"保存进度"                         | 只由用户覆盖       |
| `save_backup`      | 每次成功加载后，把上一份 auto 复制过来             | 读档失败时回滚      |
| `save_meta`        | 与 auto 同步                          | 存版本号、时间戳、校验和 |

迁移链：`migrate_v1_to_v2 → migrate_v2_to_v3`，逐级执行，不跳级；每级迁移函数必须幂等。读取时先校验 `v` 与 `checksum`，版本高于当前客户端则提示更新，不强行解析。迁移失败自动回滚到 `save_backup`，并上报 `save_migrate_fail` 埋点。

## 4.5 资源管线与首包控制

| 项    | 预算               | 措施                            |
| ---- | ---------------- | ----------------------------- |
| 主包   | ≤3.0MB（平台上限 4MB） | 只放首屏所需：启动图、UI 图集、角色 idle、房间背景 |
| 分包 1 | ≤6MB             | 家具图集、角色全动作、探险场景               |
| 分包 2 | ≤4MB             | 音频、照片卡、活动资源                   |
| 总包   | ≤15MB（平台上限 20MB） | 活动资源按需分包，过期活动可直接下线            |
| 音频   | 单文件 ≤80KB        | 64kbps 单声道 mp3，BGM 循环 60 秒    |
| 字体   | ≤1.2MB           | 只保留常用 3500 字子集（ttf 子集化）       |
| 首屏时间 | ≤3 秒（4G）         | 启动即显示静态小屋缩略图，资源异步加载           |

不使用远程 CDN 资源：个人主体配置域名与 HTTPS 证书的运维成本高于收益，全部分包解决。

## 4.6 性能约束

| 指标        | 目标                                            |
| --------- | --------------------------------------------- |
| 帧率        | 中端安卓（骁龙 660 级）稳定 60fps；低端机自动降 30fps           |
| Draw Call | ≤30（房间背景 1 + 角色 1 + 家具图集 1 + UI 3–5 + 特效 ≤10） |
| 纹理内存      | ≤64MB                                         |
| 堆内存       | ≤120MB，单帧 GC 分配为 0（对象池管理包袱、粒子、飘字）             |
| 同屏粒子      | ≤50                                           |
| 启动到可交互    | ≤3 秒                                          |
| 存档写入      | 单次 ≤5ms（序列化后异步写）                              |

降级策略：低端机（`benchmarkLevel < 20`）关闭阴影、粒子减半、角色动画降到 8fps、关闭天气特效。

## 4.7 原型迁移路径

1. 把原型的四项数值、9 个按钮对应的动作、衰减逻辑，整理成 `core` 的纯函数（保留原型的数值手感作为对照，但按 2.1 的参数覆盖）；
2. 角色从"字符网格绘制"改为"精灵图 + 动画状态机"，状态机状态与原型 8 个动作一一对应并扩展到 14 个；
3. 家具从"场景对象数组"改为 `itemId + placed` 结构，支持增删；
4. 存档从单 key 改为多槽；
5. 渲染分辨率从 600×450 改为 750×1334（见 10.1）；
6. 原型的"调试色条/自检闪屏"两处问题在迁移时直接消除，不做兼容。
